# 2.2.5-enchant-test1

Base published 2.2.4; portable factory from successful probe2. No new hooks/event sinks/polling. New code runs only in existing game-thread snapshot/apply/reclaim/lifecycle lanes. Normal sets without enchantmentRecipe metadata remain on their old route; new recipe resolution is gated by the existing prefer-enchanted option. Snapshot/update explicitly captures portable enchantment data, old preferences are not silently promoted.

Item adds an optional versioned enchantmentRecipe.signature, validated by the probe2 bounded schema. It coexists with smithing; even health1 recipes carry scoped original identity. Signature and smithing health must agree. Unknown versions or unsupported new captures fail explicitly. No new-game-unstable ENCH FormIDs are exported. User custom names, poison and mod-private individual data remain unsupported.

The existing singleton smithing generation transaction is generalized to health1 and an optional enchantment. Exact original identity wins; then a known generated/retained profile of the same recipe; otherwise generate if permitted. Factory output is compared without rewriting shared ENCH. Only a new runtime-sized list receives ExtraEnchantment and health. Original item counts/data are not mutated by reproduction. The existing UID allocation, strict before/after/count proof, bounded engine retag and failed-add retry stop remain. An enchantment must exactly equal the recipe in the fresh-item proof; presence alone is no longer considered a mismatch for this path.

GeneratedPerformance adds the canonical recipe string. Exact initial enchantment does not prevent cleanup; absent/changed/unsupported enchantment does. Health is ignored only in enchantment comparison, separately protected when higher than the initial value or nonfinite. Modified profiles retain the original recipe association for reuse and never gain deletion claims merely from matching an existing possession. Ordinary original custom-enchanted possessions remain outside the ledger. Existing transfer invalidation, identity invalidation, guards and exact-instance deletion apply to this map automatically.

Persistence: original ITEM/PERF layouts unchanged. Enchanted reproduction evidence uses EPRF (0x45505246) v1: form4/owner4/id2/health4/flags1/length4/UTF8 signature, 19+length bytes, bounded <=16384 bytes per signature and <=10000 profiles. Only flags1/3 valid; recipe validates and health must match before a profile is accepted. Duplicate performance evidence disables it. Missing/invalid evidence falls back to preserving custom-enchanted items, not base-form deletion. Retained profiles may be persisted without ITEM claims. Older releases ignore EPRF and conservatively protect custom enchants.

Tests extend JSON preset roundtrips (plain/tempered enchantments and scoped identity), mismatched health/unknown schema rejection, actual successful two-effect probe fixture with chargeOverride=-1, exact enchantment-vs-modification comparison, and fresh singleton proof at health1. 58 selected tests; runtime integration remains to be checked.

Evidence for the isolated probe: outputs/enchantment-probe-evidence-20261118 stores the successful two-effect health1.5 log and user confirmation boundaries. It does not prove this integrated build's cleanup or timing.

Source provenance: same CommonLibSSE-NG 10.1.0 bundle and native BGSCreatedObjectManager::AddArmorEnchantment path as probe2; no Papyrus bridge. Shared dynamic-enchantment reuse and repeated equipment cycles are newly relevant runtime checks. The factory's runtime FormID is logged so reuse can be observed.
